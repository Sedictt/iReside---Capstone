Access Control Strict Two-Role Human User Model

Strict Two-Role Human User Model

Per system rules, iReside implements a strict two-role model with zero admin role:

  • Landlord: Property owner. Manages properties, unit maps, leases, invoices, and maintenance.
  • Tenant: Resident occupant. Signs digital leases, submits payments, logs maintenance tickets.

Service Role Operational Model

Automated processes that require cross-tenant or system-level access use secure service role tokens:

  • Automated Billing Cron: Daily midnight worker generates recurring rent and overdue charges.
  • Workspace Initialization (/api/setup/launch): Bypasses client RLS to stamp initial configuration.
  • Disaster Recovery & Seeding: Dedicated CLI maintenance scripts run via service role key.

Access Control Matrix

Resource / Scope Landlord Tenant Service Role
Property Configuration Read / Write (Own) Read Only (Assigned) Full Bypass
Lease Contracts Create / Sign (Own) Sign / View (Own) Full Bypass
Payment Verification Verify / Reject Submit / View (Own) Automated Audit
System Initialization Execute Launch No Access Atomic Write
Submeter Readings Record & Bill (Own) View Bills (Assigned) Automated Billing
Repair Work Orders Assign & Close (Own) Create & View (Own) Work Order Worker
Emergency Spare Key Reset & Generate (Own) Reset & Generate (Own) Bcrypt Hash Engine

Human Role vs. Service Role Boundary Specifications

Security Boundary Design Constraint Enforcement Architecture
Zero Human Admin No master user exists. Database lacks admin enum values.
Service Automation Background tasks use tokens. Bypasses RLS through server credentials.
Role Segregation Landlords cannot access tenants. Strict foreign key tenant checks.
Data Flow Invariant: External entities never communicate directly without mediating processes.

Security Governance Row-Level Security Policies

PostgreSQL Row-Level Security (RLS) Architecture

Every table in the iReside database enforces strict Row-Level Security. Unauthenticated queries return zero rows:

Table Command Target Role Policy Condition
properties SELECT, UPDATE Landlord landlord_id = auth.uid()
leases SELECT Tenant tenant_id = auth.uid()
invoices SELECT Tenant lease_id IN (SELECT id FROM leases WHERE tenant_id = auth.uid())
payments INSERT Tenant tenant_id = auth.uid()
maintenance_tickets INSERT, SELECT Tenant tenant_id = auth.uid()
utility_readings SELECT Tenant unit_id IN (SELECT unit_id FROM leases WHERE tenant_id = auth.uid())
utility_readings ALL Landlord property_id IN (SELECT id FROM properties WHERE landlord_id = auth.uid())
announcements SELECT Tenant property_id IN (SELECT property_id FROM leases WHERE tenant_id = auth.uid())

Authentication 2FA Engine & Session Guards

Two-Factor Authentication (2FA) Lifecycle

iReside implements mandatory email-delivered 6-digit OTP verification for secure sessions:

  1. User submits credentials at /login via Supabase Auth PKCE flow.
  2. Server generates an ephemeral 6-digit cryptographic token (10-minute expiry).
  3. Token is dispatched via transactional SMTP to the verified email.
  4. User inputs token; upon verification, Supabase issues signed JWT and refresh tokens.

Authentication Threat Model & Defense Mechanisms

Threat Vector Risk Level Defense Architecture
Brute Force Login High Rate limit: 5 failed attempts per IP.
Session Hijacking Critical HTTP-only SameSite cookies and TLS 1.3.
OTP Replay Attack Medium 10-minute expiry on single-use OTP codes.
Client Lock Stalls High Background non-blocking auth refresh execution.

Session Token Specifications & Lifecycle

Token Identifier Storage Medium Validity Window
Access Token (JWT) Secure HTTP-only cookie 60 minutes with auto-refresh.
Refresh Token Encrypted HTTP-only cookie 30 days rolling validity window.
Setup Cookie Browser session cookie Instant client navigation signal.
CSRF Token Client Header Protects state-changing REST endpoints.

Next.js Edge Middleware Evaluation Pipeline (middleware.ts)

Route Pattern Session Requirement Middleware Action
/landlord/* Valid session with Landlord role Redirects to login if unauthenticated.
/tenant/* Valid session with Tenant role Redirects to login if unauthenticated.
/setup/* Pending setup profile flag Enforces onboarding wizard completion.
/api/cron/* Valid CRON_SECRET header Rejects missing tokens with HTTP 401.
/login, /signup Anonymous / Unauthenticated Redirects active sessions to home dashboard.
Client-side SDK token refreshes must NEVER be awaited on the critical navigation path.

Cryptography Emergency Spare Key Architecture

The Emergency Spare Key Architecture

The Emergency Spare Key provides failsafe account recovery when losing phone or email access:

Cryptographic Engine Specifications

Parameter Cryptographic Standard Operational Implementation
Entropy Source CSPRNG 128-bit random bytes Secure browser crypto API source.
String Format 16 uppercase alphanumeric chars 4 blocks separated by hyphens.
Hashing Algorithm Bcrypt (Cost factor 12) Plaintext key is never stored in DB.
Revocation Rule Single-use consumption rule Key is deleted upon successful recovery.

Account Recovery Verification Protocol

Recovery Step Verification Check Expected System Response
1. Submit Email Verifies user profile exists Checks active user in PostgreSQL.
2. Submit Spare Key Constant-time hash verification Prevents timing side-channel attacks.
3. Session Reset Revokes existing refresh tokens Issues authenticated recovery session.
4. Key Rotation Generates new spare key Old key is rendered permanently invalid.

Atomic Recovery Lifecycle (/api/auth/spare-key-recovery)

The recovery endpoint validates the submitted key hash using constant-time verification.

Upon verification, existing tokens are revoked and a replacement key is generated.

Emergency Spare Key Error Handling & Failure Matrix

Failure Scenario Detection Mechanism Recovery Resolution Runbook
Invalid Key Input Constant-time hash comparison fails Prompts retry with clear inline error message.
Consumed Key Reuse Database flag checks key deletion Rejects used key; guides user to support.
Rate Limit Exceeded Exceeds 5 attempts per IP Throttles requests for 15 minutes.
Senior Landlord Invariant: Recovery keys use the Emergency Spare Key physical metaphor. Touch targets measure at least 48px.

System Lifecycle Turnkey Workspace Launch

The Turnkey Workspace Launch Lifecycle

The 5-stage onboarding pipeline guides new landlords through required system initialization:

5-Stage Onboarding Route Locking Matrix

Stage Identifier Accessible Routes Locked Routes
Stage 1: Property no_property /landlord/properties, /new All other sidebar navigation items.
Stage 2: Unit Map no_unit_map /landlord/unit-map Operations and Finance workspaces.
Stage 3: Billing Rails no_billing_rails Dashboard, Properties, Utility Finance Hub and Tenant records.
Stage 4: Tenants no_tenant Dashboard, Properties, Tenants Deep operational financial pages.
Stage 5: Dashboard setupCompleted All production workspaces None (All features fully unlocked).

Launch Atomic Validation Contract (/api/setup/launch)

Validation Check Required Entity Failure Behavior
Property Exists At least 1 registered property Rejects launch with HTTP 400.
Units Configured At least 1 configured rental unit Rejects launch with HTTP 400.
Utility Rates Set Non-zero water and electric rates Rejects launch with HTTP 400.

Atomic Finalization Rail

When the landlord completes configuration, the workspace executes an atomic launch sequence:

  1. Client submits setup state to /api/setup/launch.
  2. Service role verifies property and utility rates exist.
  3. Sets is_setup_completed = true in the profile database record.
  4. Sets HTTP-only cookie ireside_setup_completed=true for immediate middleware evaluation.
  5. Redirects to /landlord/dashboard via router.replace.
Navigation Rule: Use router.replace to avoid back-navigation loops into setup wizards.

Technical Glossary

RLS: Row-Level Security in PostgreSQL restricting row access per user session.
JWT: JSON Web Token used for cryptographically signed stateless session verification.
Service Role: Privileged PostgreSQL role that bypasses RLS for administrative workers.
Capacitor 7: Cross-platform runtime executing the web app inside an Android WebView.
Vercel Cron: Serverless scheduler invoking authenticated API endpoints at defined intervals.
Bcrypt: Adaptive cryptographic hash function used for Emergency Spare Key verification.
CSPRNG: Cryptographically Secure Pseudo-Random Number Generator.
PgBouncer: Lightweight connection pooler for PostgreSQL database.
WAL: Write-Ahead Logging ensuring durability and point-in-time recovery.
PKCE: Proof Key for Code Exchange securing authorization flows.
RTO: Recovery Time Objective specifying maximum allowable downtime.
RPO: Recovery Point Objective specifying maximum allowable data loss.
